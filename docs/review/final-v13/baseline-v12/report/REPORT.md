采购员自己去各个商家选购或记录商品，把照片、价格、货号、包装等数据记下来；自己复看、整理和比较，最终得到参考样式的商品 Excel。

## 1 一页结论

方向保持简洁：**选商户 → 记录商品 → 自己整理/比较 → 导出商品 Excel。**

现有产品已经有商户入口、日期范围、照片处理、公司表格模板和真实 Excel 输出基础。优先修保存可靠性、带图下载、复看效率和范围一致性，不推倒数据模型。

| 重点 | 当前问题 | 最小处理 |
|---|---|---|
| 记录可靠 | 已有商品有本机未保存修改，从卡片打开可能读不到，保存后草稿被删 | 恢复选择、版本比较、明确草稿生命周期 |
| 带图 Excel | 后端按 4MiB 分段，实际容器通道有限制，大文件链路未验 | 缩小嵌图、协商安全分段、实测大文件 |
| 本地空间 | 图片与导出文件累计，可能挤占草稿空间 | 固定缓存命名、按引用保护的清理 |
| 自己整理 | 返回列表清空分页/滚动；核对一件要反复打开返回 | 保留位置、顺序整理、明确人工字段与 AI 建议 |
| 商品比较 | 两件比较受当前范围限制，差异不明显、模式易残留 | 保留两件比较，清楚范围与差异，不建候选组 |
| 导出范围 | 日期/商户已支持；搜索及缺项筛选不一定带入 | 当前文件包含什么必须说清；逐步支持所选/筛选 |
| 视觉 | 头部占首屏、重要信息小而浅、保存按钮缺文字 | 紧凑列表可切换、大图保留、主次按钮清楚 |
| Excel 对齐 | 已完成不少自适应排版，不能把旧问题全算未完成 | 逐项复核当前代码与真实文件，重点公式、图片、缺值 |

三项优先风险为草稿丢失、带图下载、本地文件累计；具体触发量和手机表现仍需实测。不能再用“上线几周内必然失败”的时间表述。

## 2 概念和结构：保留记录工具的简单模型

### 2.1 看货与商品不是两套业务

“看货”是现场入口：今天去哪几家、从这家店继续记。 “商品”是自己的资料库：跨日期查找、补数据、比较、导出。两者引用同一份商品，不复制出一套订单数据。

保留三个 tab：看货、商品、我的。我的包含个人资料、收藏、本机草稿和 Excel 格式；导出与整理放在商品上下文，不要求去我的找主操作。

现状问题包括隐藏的当前商户/日期状态、多个近似范围组合和过时帮助。证据：`miniprogram/utils/product-page.js:18,43`，`miniprogram/pages/help/index.wxml:1`。修法是显式显示日期与商户，导航传明确参数，不增加业务层。

### 2.2 商户只需要准确，不必先做 CRM

目前按商品 `supplier` 文本分组；同名会合并，错字会拆开。店名和摊位输入混在一起，回访难复用。证据：`src/lib/db.ts:161`、`src/lib/quotation-export.ts:285`、`miniprogram/pages/projects/index.wxml:15`；历史 SQL 复现 `../ia-review/visits-sim.mjs`。

首期拆开店名和摊位、联想已有商户、显示可能重名即可。完整档案迁移和自动合并不作为前置要求。真正需要独立商户 ID 时，应先用不同店同名的真实案例设计迁移；不能仅按名称自动合并既有记录。

新品必须有明确商户；从历史日期录新货按今天首次保存日记录并提示；保存并继续只沿用当前店，不能靠旧缓存猜商户。这些入口规则已有实现与历史回归证据，不应重做成新“订单上下文”。

### 2.3 “已核对”只讲资料，不讲买不买

当前 `confirmed` 是人工检查标记，不是采购决定；收藏和评分是个人偏好。它们都不能自动解释成要买、不买或取消。

历史问题：改任意字段容易撤销核对，提示文案未呈现。证据：`miniprogram/pages/editor/index.js:248,305`、对应 WXML；`../verify-states/`。

短期先说明核对什么、仅关键事实变化需要重新检查、撤销时提示。不要直接把全部旧 `confirmed` 自动改成“资料齐全”；资料缺项由字段推算、AI 值是否确认由来源判断，二者独立。

缺价格、每箱数、体积是合法记录，不阻断拍照保存或商品表导出。提醒“缺几项”，不能制造“必须把全部核对清零”任务。

### 2.4 删除不等于不喜欢

收藏、评分、评价继续保留；不收藏不代表淘汰，不引入全局淘汰状态。回收站是移除记录，不是采购决定。永久删除须确认，恢复和引用保护需可靠。

旧采购整理入口保持隐藏，不恢复成主流程，也不删除用户既有私有文件或数据。未来若确需停用，要另做兼容与保留策略。

## 3 现场记录：减少操作，先保证内容不丢

### 3.1 字段顺序

首屏保留当前店、照片、整段描述、名称/价格/货号；包装规格按需要展开。照片里看不出价格、每箱数、箱规时，方便手填；未知留空。

每箱数和起订量不同；实际数量含 0 优先，只有未手填时才可由箱数×每箱数量推导。不把起订量填成采购量，不从中包 QTY 猜整箱数。真实照片观察见 `../real-order-result.json` 的 photos，模型是否会误读仍需本机评测。

系统相机保留。现场拍照直开相机；相册是次要补图入口。外箱尺寸可以一个输入框加计算预览，但不猜单位。上次用过的包装数量可作为建议，不预选。

不画页内相机、录音按钮或常驻数字键盘，避免把后期实验当作已可交付能力。

### 3.2 保存与草稿

- 已保存商品存在同 ID 本机修改时，打开前给“继续未保存修改/查看已保存版本”选择，不直接删除。
- 保存失败保留文字和所有照片；切后台、断网、版本冲突都不清表单。
- 保存返回与保存并继续有明确文字和主次。
- “本机已保存”与“云端已保存”分别表达；尚无可靠多件持久队列前，不承诺保存后立即继续。
- 重试先检查幂等回执；上传中离开页不创建重复商品。

证据：`miniprogram/pages/editor/index.js:22,58,464`、`miniprogram/utils/product-page.js:350`；`../verify-prod/repro-draft-loss.js`。

### 3.3 照片整理

参考表中有一行多图、陈列盒与单品图，也有来自微信的目录图和桌面旋转图。它们首先服务认货，不表示所有字段可从图自动识别。证据：`../real-order-result.json` photos。

先做好：封面可选、照片顺序清楚、保存时显示进度、Excel 图片不变形。旋转/裁剪和聊天导入是后续局部增强，不为照片类别建凭证系统。

现状约 19 个动作/件是脚本拆分点击、输入、系统相机动作后的估算，系统步骤不是真机实测；见 `../capture-r2/runs/`。目标用跟岗计时衡量，不继续承诺“≤8 动作、0 跳转”。

## 4 自己复看、整理和比较

### 4.1 返回保留位置

当前页面显示时可能清空列表、回第一页。证据：`miniprogram/utils/product-page.js:19,31,117`。

修复验收：第 40 件打开编辑 → 保存返回 → 原筛选、分页和滚动仍在；只替换变化的那一行，不重新下载全部照片。切日期/商户时才清除不再适用的状态。

### 4.2 资料整理入口

商品页直接“整理资料”，按当前范围顺序查看照片与字段，保存并下一件，允许跳过。无 AI 时也能人工整理；AI 建议逐项可见，不一键采用看不到的值。历史手动核对、缺项和 AI 值确认不混成同一种勾。

批量选择必须说明“已加载的 n 件”还是“当前筛选全部 n 件”，不能静默只选前 50 件。支持所选导出时服务端与前端使用同一集合，超限明确报错。

### 4.3 比较保持简单

先保留两件比较，改善跨日期选择和返回恢复；不做同款候选组、入选、淘汰或下单按钮。差异高亮，价格单位与币种显示；口径不明不比较“更便宜”，不同币种不自动换算。

证据：`miniprogram/utils/store.js:21`、`miniprogram/pages/compare/index.wxml:16`、`miniprogram/utils/product-page.js:64,277`。

## 5 商品 Excel：范围与结果比业务状态重要

### 5.1 导出规则

默认当前日期、所有商家、全部已保存有效商品、带图；单店入口保留该店选择。可选连续日期范围含首尾，按北京时间首次保存日，而非修改日。收藏旧入口保留自身范围。

同一精确商户名称跨日合并 sheet；同货号多次记录不自动去重、相加或取最新。草稿和回收站排除；备注写“取消”不自动排除。“仅已核对”是显式资料筛选，不是采购口径。

搜索、缺价等筛选当前不支持传入时，先告诉用户将导出日期/商户范围全部记录，再让其选择；不能假装已经支持。后续增加筛选/所选应有同源计数与预览。

导出页看见起止日期、商户数、商品数、带图方式、缺项数和实际表尾。缺项提醒允许继续，不强迫采购决定。没有记录时不生成空文件。

### 5.2 参考表的真正验收口径

`docs/HANDOFF.md` 2026-10-21 16:03 的最终参考式输出记录：10 商家、38 条商品、44 张图、10 行商户 TOTAL；全部记录口径为 96 箱、24,876 件、商品金额 79,260、体积 7.320 m³。

这些是特定样本的历史验收数字，不是所有文件都必须有的固定值。原表 TOTAL 的 89 箱、69,454.80 元与“剔除取消/计入后补/加运费”的原型 90 箱、70,491.60 元是不同口径。**本产品不是下单系统，因此不把后者当正确商品表的硬指标。**

新增验收以同构合成数据为准：选择范围内全部有效记录逐行一致、图片完整、公式正确、未知与 0 区分、同商户跨日合并、同货号独立保留。真实参考 Excel 与图片只留本机，不上传做云验。

### 5.3 排版、公式和未知数

当前已有有界动态列宽、多图网格、长备注续行、独立币种 TOTAL；不能把旧报告“全部静态值/全部原样式不对”的结论无条件继承。

继续检查：

- 数量、金额、体积按字段标识写公式，列顺序变化后仍正确；明确数量优先、不完整乘数保持空值。
- 保留用户保存过的字体、列宽、行高和表头，不用新默认覆盖。
- 图片比例与清晰度兼顾，Excel 内显示尺寸与嵌入像素合理，不拉伸、不越行、不互相重叠。
- 长备注续行只在主行计数；含续行的表不启用会拆散备注的排序筛选。
- 不把单价、每箱数、单箱体积相加；不同币种不混加。
- 合计中有未知数时不写完整总计；显示缺项，不把未知当 0。明示商品金额不含未记录的其他费用。
- 条码是可选字符串，保留前导零，不强制69前缀、13位，不生成零售条码。
- 已生成文件在同范围返回后可重新打开；范围改变才失效，迟到任务结果不能覆盖新范围。

证据：`src/lib/quotation-export.ts`、`miniprogram/pages/export/index.js:38,148,174`、`docs/UX-NOTES.md` 的 2026-10-21 最终自适应表格段。

### 6.1 分段不能只看原始字节数

平台官方历史文档记录 callContainer 回包上限 1000KiB；实际路径见 `miniprogram/utils/container.js:117`。必须实测此通道的二进制传输表示；如果涉及 base64/JSON 包装，应计入编码开销，不能只看原始块长。建议原始 640KiB 作为 PoC 上限候选，**实际传输响应≤900KiB** 才算符合保守预算。768KiB 原始数据经 base64 已是 1MiB，还没算封装，不能在未验证通道表示前沿用旧建议。

旧客户端检查4MiB固定元信息，后端不能直接替换值。可用 capability/协议参数协商：先部署同时支持旧/新协议的服务端，再发布新客户端。兼容旧协议不表示旧大文件已经可用，旧大文件应明确提示不支持，不破坏已有小文件路径。

最终是否改用云存储下载，需要用户确认架构通道和平台配置；不在本轮擅自开启公网兜底。

### 6.2 文件清理必须保护记录

清理只针对明确索引的可再下载缓存和过期导出文件。草稿照片、待上传照片、正在分享的文件、被编辑器引用的文件均保留。受保护文件超预算时给空间提示，不静默删内容。

50–60MB 缓存预算和7天导出保留期仅是候选参数，需测；不递归清空 `USER_DATA_PATH`，不把“删除整个小程序”当正常解决方案。

### 6.3 其他规模问题

## 8 执行顺序：小步修，不扩系统

旧handoff的“先S0”“12–16人日”“两名开发2–3个月”都是旧方案建议，不是负责人确认排期。当前按可靠性和记录效率分小批，完成一批再确定下一批，不承诺未经估算的总工期。

### A 可靠性

1. B1草稿恢复与删除保护。
2. PF1缩嵌图、安全分段与旧客户端兼容。
3. PF2受引用保护的本地缓存清理。
4. 以合成数据验证大文件、并发与失败恢复；补手机验收。

### B 使用效率

1. 保存按钮文字与主次；相机直开；包装展开状态记忆。
2. 商品返回保留分页、滚动和筛选。
3. 核对撤销规则和提示；明确缺项与AI值确认。
4. 日期/商户/搜索范围可见，导出结果一致；暂不支持的范围明确提示。
5. 列表请求与限流，紧凑视图和差异高亮。

### C Excel闭环与局部增强

1. 同构样本逐行/多图/公式/缺值/币种检查 + 桌面Excel直接打开。
2. 整理资料的顺序浏览，避免反复返回。
3. 有实际需求再加导出所选、照片旋转/裁剪、商户联想。

不做：订单/采购批次、复杂商户档案、发送确认、交货状态、付款或仓库流程。旧采购原型保留为历史技术试验，不接进主流程。

## 9 尚需真实使用者验证

只问直接影响记录与Excel的问题：

1. 现场每件常填哪些字段？哪些回来补？
2. 多图是一件一记还是先拍再整理？错店或找不到货最常怎么发生？
3. “已核对”现在具体检查哪些内容？改什么需要重看？
4. 复看用手机还是电脑Excel？紧凑列表/大图哪种更合适？
5. 日期范围、单店、收藏和所选，哪种最常导出？
6. 参考表必须保留哪些列、图片位置、公式和表尾文字？哪些可简化？
7. 每天实际记录量、弱网、文件大小和手机可用空间怎样？

不把客户身份、公司收款/仓库分工或装柜流程作为当前开发的前置访谈。
